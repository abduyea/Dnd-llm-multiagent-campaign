Overview

What I Built

🎲 The Application
  • Browser-based D&D campaign manager
  • Create campaigns, characters, and game sessions
  • Submit player actions — AI narrates the outcome
  • Real-time streaming narration via Server-Sent Events
  • NPC dialogue, memory persistence, session summaries
🤖 The AI System
  • DM Agent — narrates turn outcomes (2-3 cinematic sentences)
  • NPC Agent — generates in-character spoken dialogue
  • Memory Agent — extracts story facts to a SQLite table
  • Context Builder — assembles world/character/history context
  • Summary Agent — writes session recaps when sessions end
The Problem

Why This Needed to Exist

👥 Scheduling Problem
  • Traditional D&D needs 4–6 coordinated players
  • Requires an experienced Dungeon Master
  • Sessions take 3–5 hours to organize
🤖 AI Gap
  • Existing chatbot DMs have no rules engine
  • They invent dice results and ignore game mechanics
  • No persistent story memory across sessions
☁️ Cloud Dependency
  • Most AI tools require paid API subscriptions
  • User data sent to third-party servers
  • Latency and cost degrade real-time play

The core insight: separate mechanics from narrative. Let the engine enforce the rules. Let the AI tell the story.

Development Process

How It Was Built

Phase 1 — V2 CLI Engine
Built event-sourced CLI engine (V2/). LLMs play both player characters and DM autonomously. Structured <intent /> tag protocol forces valid actions. 15-room dungeon demo with 2 PCs and 6 NPCs.
Phase 2 — FastAPI Backend
Rebuilt as async FastAPI service. SQLite persistence, Alembic migrations, 7 REST + SSE endpoints. Orchestrator coordinates engine + 5 AI agents per action.
Phase 3 — Web Frontend
Vanilla JS SPA with dark D&D theme. Campaign manager, character sheets, enemy tracker, streaming narration panel. Bootstrap 5, Cinzel + Garamond fonts.
Phase 4 — Testing + Cleanup
383 test functions across 14 files. Removed ChromaDB (unused, ~1GB Docker weight). Cleaned repo for GitHub. Added Docker Compose for one-command deployment.

Challenges

What I Had to Figure Out

LLM JSON Reliability
Local models sometimes return prose instead of valid JSON for memory/NPC extraction.
→ Built keyword-extraction fallback. Regex scans narration for NPC/location/item signals when JSON parsing fails.
Think-Block Stripping (qwen3)
qwen3 emits <think>...</think> reasoning blocks before the actual response, including during streaming.
→ Implemented real-time buffered state machine to suppress think blocks while streaming tokens without blocking the stream.
Context Window Management
Long sessions (20+ turns) would exceed the LLM's context window, degrading narration quality.
→ Session summary compression: beyond turn 20, a Summary Agent writes a chronicle, and raw history is capped to the last 4 turns.
NPC Name Extraction
Extracting NPC names from narration text was unreliable — D&D spell names (Fireball, Shield) look like proper nouns.
→ Built a stop-word + D&D keyword blocklist (120+ terms) applied before NPC name candidate extraction.
ChromaDB Bloat
ChromaDB was in the original dependency list but never called in runtime code — adding ~1GB to the Docker image.
→ Audited all imports, confirmed zero runtime usage, removed from all dependency files and Docker layers.
Attack Target Resolution
Frontend's enemy tracker stores enemies but they aren't registered as DB characters — attack engine couldn't find them.
→ Enemy context extraction: parses "[Target: Name]" prefix in action description, builds a synthetic CharacterState from frontend HP/AC data.

Lessons Learned

What This Project Taught Me

🔧
New Skill: Async Python at scale
First time building a full async FastAPI application with SQLAlchemy async. Learned how connection pooling, async context managers, and SSE generators interact.
🤖
New Skill: LLM prompt engineering for structured output
Learned to design system prompts that constrain LLM behavior — strict rules, second-person tense, forbidding specific words. Built fallbacks for when the model ignores constraints.
📐
Improved: Software architecture (separation of concerns)
"LLM proposes, engine disposes" — keeping deterministic rules separate from AI narration made testing possible and the system trustworthy.
🧪
Improved: Test-driven development with mocking
383 tests using in-memory SQLite overrides and patched Ollama client. Learned that untested fallback paths are where real bugs hide.
❌
What Failed: Letting AI resolve mechanics
Early prototype had the LLM decide if attacks hit. It was inconsistent and impossible to test. Replacing it with pure math was the right call.
